# Releasing PushKit

PushKit ships via a tag-and-walk-away pipeline. Pushing a `v*` tag from `main` triggers the full release workflow (`.github/workflows/release.yml`); no other manual steps are required.

This is the maintainer runbook. For day-to-day development setup see [CONTRIBUTING.md](CONTRIBUTING.md).

## Cutting a release

```bash
git tag -a v0.1.0-rc.1 -m ""
git push origin v0.1.0-rc.1
```

That is the only manual action. The pipeline runs automatically and produces:

- **PyPI:** `pushkit==0.1.0rc1`, published via OIDC Trusted Publishing. The git tag `v0.1.0-rc.1` is normalized to the PEP 440 wheel version `0.1.0rc1`. Install it with:
  ```bash
  pip install --pre pushkit==0.1.0rc1
  ```
- **GitHub Release:** marked as prerelease for `-rc`/`-alpha`/`-beta` tags. Assets: `pushkit-server-setup.exe` (Windows installer), `pushkit-android.apk` (Android debug APK), and `SHA256SUMS` (asset integrity). Release notes are generated by `git-cliff` from Conventional Commits.

Target wall time: ≤ 15 minutes for the first release.

## Pipeline overview

The jobs form a DAG, not a strict line — the `version` job fans out to several builders that run in parallel. Each job's `needs:` are noted in parentheses.

1. **`tag-guard`** — refuses tags not reachable from `origin/main`.
2. **`version`** (needs `tag-guard`) — the single source of truth for version strings. Emits three outputs every downstream job consumes instead of re-stripping inline:
   - `version` — the raw tag, e.g. `v0.1.0-rc.1`
   - `stripped` — the tag without the leading `v`, e.g. `0.1.0-rc.1`
   - `pep440` — the PEP 440-normalized wheel version, e.g. `0.1.0rc1`
3. **`retest-{backend,cli,android}`** (needs `version`) — re-run the pre-merge CI gates against the tagged commit.
4. **`build-cli-wheel`** (needs `version`, `retest-*`) — `make build-wheels VERSION=<pep440>`. The wheel must use the PEP 440 form (`0.1.0rc1`), not the tag's `-rc.N` form, or PyPI rejects the filename.
5. **`build-backend-binary`** (needs `version`, `retest-*`) — cross-compiles `pushkit-server.exe` on Linux (`GOOS=windows GOARCH=amd64 CGO_ENABLED=0`) with `-ldflags "-X main.Version=<stripped>"`, then uploads it as an artifact.
6. **`build-backend-installer`** (needs `version`, `build-backend-binary`; runs on `windows-2022`) — downloads the binary artifact, installs NSIS 3.12, verifies the bundled `SimpleSC.dll` SHA-256, and runs `makensis /DVERSION=<stripped>`.
7. **`build-android-apk`** (needs `version`, `retest-*`) — sets `versionCode` from the commit count and `versionName` from `<stripped>`, then builds the debug APK.
8. **`generate-changelog`** (needs `version`, `retest-*`) — `git-cliff --unreleased --tag <tag>` over full history.
9. **`publish-pypi`** (needs `build-cli-wheel`, `build-backend-installer`, `build-android-apk`, `generate-changelog`) — runs in the `pypi` environment and publishes via OIDC Trusted Publishing using `pypa/gh-action-pypi-publish@release/v1` with `attestations: true` (PEP 740 / Sigstore provenance).
10. **`create-github-release`** (needs `version`, `publish-pypi`, `build-backend-installer`, `build-android-apk`, `generate-changelog`) — `softprops/action-gh-release@v3` uploads the installer, APK, and `SHA256SUMS`; release notes come from the generated changelog.
11. **`post-publish-linux`** + **`post-publish-windows`** (needs `create-github-release`) — fresh `pip install --pre` and `pushkit --version`, APK `aapt` version probe, `sha256sum -c SHA256SUMS`, silent install and `pushkit-server --version` smoke test.

## Rollback

Once a tag is published it is final. We do not re-run `release.yml` on the same tag.

If a release ships with a bug:

1. **Yank the wheel from PyPI.** Sign in to PyPI and mark the version yanked. Yanking blocks new resolutions of that exact version but keeps pinned installs working.
2. **Cut a new release tag** at the fix commit (for example `v0.1.0-rc.2`). The full pipeline runs again.
3. **The original GitHub Release stays** — delete its assets manually via the web UI or `gh release delete-asset` if needed. The tag itself stays in git history.

### Partial-failure recovery

If `publish-pypi` succeeds but `create-github-release` fails, a PyPI package exists with no matching GitHub Release. The failed run emits an `::error::` annotation with this same guidance. Recover by either:

1. Yanking the PyPI release: `pip install twine && twine package yank pushkit <version>` (requires a PyPI API token with the yank scope), or
2. Fixing the root cause and re-tagging as the next prerelease (e.g. `-rc.N+1`) to trigger a clean run.

## Required GitHub repo settings (one-time, manual)

These are configured outside CI; documented here for future maintainers:

1. **PyPI Trusted Publisher:** owner `jayteealao`, repository `PushKit`, workflow filename `release.yml`, environment `pypi`. Configure under PyPI → Account settings → Publishing.
2. **Tag-protection rule:** restrict `v*` tag creation to maintainers via Settings → Rules → Rulesets. The `tag-guard` job is a CI-level backstop; this is the GitHub-level guard.
3. **`PYPI_API_TOKEN` repository secret** (break-glass only): a PyPI API token scoped to the `pushkit` project. The default publish path is OIDC; this secret exists only for the OIDC-outage recovery path below.

## Break-glass: PyPI OIDC outage

If `pypa/gh-action-pypi-publish` cannot acquire an OIDC token (PyPI-side outage, clock skew, environment misconfig), temporarily swap the `publish-pypi` step in `release.yml`:

```yaml
- uses: pypa/gh-action-pypi-publish@release/v1
  with:
    packages-dir: dist/
    password: ${{ secrets.PYPI_API_TOKEN }}   # break-glass only
    attestations: false
```

Push the tag again with a bumped `-rc.N+1`. **Revert this change** before merging the next normal release PR — the default path is OIDC with attestations enabled.
