## Stage 2 — Shape (2026-05-22T22:26:43Z)

### Round 1 — What does the feature do?

- **Artifact failure mode:** All-or-nothing. Any failing artifact aborts the GitHub Release entirely. PyPI may publish first; that's the accepted residual risk (recoverable via yank).
- **Tag-on-main enforcement:** Job-level guard (CI checks `git merge-base --is-ancestor`) PLUS GitHub branch-protection rule restricting `v*` tag creation to maintainers. Defense in depth.
- **Pre-merge CI depth:** Lightweight pre-merge (backend tests, CLI tests, Android assembleDebug + lint, commitlint), heavy builds reserved for the tag-driven release workflow. Fast PR feedback.
- **User outcome:** Tag-and-walk-away. Maintainer pushes the tag, comes back to a complete GitHub Release. No manual asset uploads, no post-tag commands, no draft-to-publish promotion gate.

### Round 2 — How does the feature behave?

- **Backend version flag:** Add `var Version = "dev"` to `backend/cmd/server/main.go` plus a `--version` flag. CI injects via `-ldflags -X main.Version=$TAG`. Mirrors the CLI pattern at `cli/main.go:11`.
- **Commit-history backfill:** Forward-only enforcement. Existing 5 commits stay as-is. `git-cliff --unreleased --tag v0.1.0-rc.1` produces whatever it can. Thin first changelog accepted.
- **Android versionCode source:** `git rev-list --count HEAD` at build time. Requires `fetch-depth: 0` in CI. Rewritten into `android/app/build.gradle.kts` in-place during the build job; not committed back.
- **PyPI publish failure recovery:** Yank + new -rc patch tag. Per ship-plan Block E and the `pypi-trusted-publish-failure` playbook in Block F.

### Round 3 — What does the feature look like?

- **CI file layout:** Separate `.github/workflows/ci.yml` (PR + push-to-main gate) and `.github/workflows/release.yml` (tag-driven artifacts). Two files, clean separation.
- **Hook runner:** Lefthook (single Go binary, language-agnostic). `lefthook.yml` + `commitlint.config.cjs` checked in. CI backstop via `wagoid/commitlint-github-action@v6` for `--no-verify` bypass defense.
- **NSIS installer scope:** Full installer with optional Windows service component (not just minimal silent-capable). Service registration optional at install time; full upgrade/uninstall lifecycle automation.
- **SHA256SUMS:** Single file for all release assets (`<hash>  <filename>` per line). Generated by a tail job in release.yml.

### Round 4 — What can go wrong?

- **Service install depth:** Full lifecycle automation. Installer detects existing service via `sc query`, stops + replaces + restarts on upgrade. Uninstaller cleans up service registration. Handles UAC elevation prompts.
- **`--no-verify` bypass defense:** CI backstop fails the PR. `wagoid/commitlint-github-action@v6` validates every PR commit; failing commits block merge.
- **Secrets surface:** OIDC + sealed backup `PYPI_API_TOKEN`. Default path is OIDC Trusted Publishing (zero secrets); a sealed GH secret `PYPI_API_TOKEN` exists as break-glass for OIDC outages. Documented as "manual escape hatch only."
- **URL fix scope:** Fix both `Makefile` and `release.yml`. Verify wheel metadata's `Project-URL` after rebuild. Go module path renames stay OUT of scope.

### Round 5 — Where are the boundaries?

- **Confirmed out of scope:** Backend DB migration tooling AND Windows code-signing of the installer.
- **Cadence:** On-demand, low frequency (1 tag every 1–4 weeks). No idempotency safeguards needed beyond the standard "tag already exists" GitHub Release error.
- **README badge:** shields.io with `include_prereleases=true`. URL: `https://img.shields.io/github/v/release/jayteealao/PushKit?include_prereleases=true&sort=semver`. Rendered at top of README under the title.
- **Backfill final answer:** Forward-only. Accept thin v0.1.0-rc.1 changelog. No history rewrite. The first new commit on `feat/ship-plan-buildout` will be the workflow's own commits authored conventionally from day one.

### Clarifications (post-Round-5)

These items were unticked in the Round-5 multi-select; surfaced for explicit confirmation:

- **Android release signing:** Stays OUT. Confirmed intake decision. v0.1.0-rc.1 APK is debug-signed. Release signing deferred to future workflow with keystore + secret rotation.
- **Go module path renames:** Stay OUT. `github.com/pushkit/{cli,backend}` import paths unchanged. Only the cosmetic URL fixes in Makefile + release.yml are in scope.

## Stage 3 — Slice (2026-05-22T22:46:55Z)

### Slicing strategy

- **Granularity:** One PR, 5 slices (user freeform). Five thin slices delivered through a single PR on `feat/ship-plan-buildout`. Slug-wide review scope from intake remains; each slice still gets its own plan/implement/verify artifacts for clean reasoning trails.
- **Delivery order:** Risk-first. `commit-hygiene` first (foundational hard edge), then `nsis-installer` (highest uncertainty), then `backend-version` (xs mechanical), then `android-versioning` (small Gradle change), then `release-orchestration` (xl integrator).
- **Tag timing:** All slices must land on main before the v0.1.0-rc.1 validation tag. No throwaway intermediate tags. Tag is the end-to-end acceptance gate.
- **Dependency model:** Sequential hard edges. `commit-hygiene` blocks all; `nsis-installer`, `backend-version`, `android-versioning` each block `release-orchestration`. The three middle slices are independent of each other (could be parallelized at plan time if appetite allows).

## Stage 4 — Plan: commit-hygiene (2026-05-22T23:44:29Z)

Two rounds of discovery questions (7 total) covering implementation choices the shape and slice left implicit.

### Round 1 — Approach

- **Commitlint major:** v21 (current, ESM, Node ≥ 20). commitlint.config.cjs still works via cosmiconfig regardless of the package's internal ESM.
- **Scope vocabulary:** Fixed enum at warning severity. Vocabulary: `backend, cli, android, ci, docs, deps, installer, release`. Promote to error severity in a future slice once vocabulary is stable.
- **CI layout:** Single `ci.yml` with 4 parallel jobs (per slice spec). Splitting commitlint into its own workflow saves nothing meaningful.
- **Action pinning:** Floating tag (`@v4`, `@v6`). Matches existing `release.yml`. Accept residual supply-chain risk for v0.x; revisit in SLSA hardening.

### Round 2 — Mechanics

- **Test invocation:** Inline per-job (no Makefile change). backend-test runs `cd backend && go vet ./... && go test ./...` directly. No new aggregator target.
- **Hook auto-install:** `package.json` `prepare` script runs `lefthook install` on `npm i`. Documented in README so contributors know to `npm install` after clone.
- **Go version:** Pin a single Go 1.24 across both Go jobs. CLI's `go.mod` declares 1.22.0; Go 1.24 compiles it without issue. Note `cli/go.mod` alignment to 1.24 as a future tidy-up (out of scope for this slice).
